# Changelog

All notable changes to `@sureq/core`. From 1.0, semver applies to the public API and the stored job format: a breaking change needs a major release.
The store contract stays experimental and may change in a minor release until it is declared stable.
Before 1.0, a minor release (0.x) could break the API; every break is listed below.

## 1.0.0 - 2026-11-17

**Upgrading from 0.3**
- 0.3 and 1.0 store jobs in the same format, so pods on 0.3.x and 1.0 can share one store during a rolling deploy, and neither goes into degraded mode.
- A store adapter built for 0.3 declares contract version 2, which 1.0 refuses. Set its `contractVersion` to `STORE_CONTRACT_VERSION` (now 1) before the rollout; the contract itself did not change (see Changed).
- Releases with different major versions are never adjacent, so while both run, every pod with a running worker emits `versionSkew` (`{ workers }`) naming the other release's workers. The event is advisory and blocks nothing; it stops once every pod runs 1.0. Finish the rollout instead of leaving both releases running.

**Changed (API decisions before 1.0)**
- The store contract (`Store`, its request and result types, `STORE_CONTRACT_VERSION`, `MemoryStore`'s contract methods and the `store` option) is marked beta: experimental until 1.1, as the docs say.
- `Schedule` is its own type with the fields the docs list. It no longer exposes the store's `rev`; `createdAt` and `updatedAt` are documented.
- A bare number is refused as a job's `keep` (`keep: 1000` was 1000 milliseconds, while the queue `retention` reads a number as a count). Write `'1000ms'` or `{ age: 1000 }`.

**Added**
- An agent skill, `skills/sureq`, installable with `npx skills add sureq-js/sureq --skill sureq`.
- New error class `UnsupportedRuntimeError` (`UNSUPPORTED_RUNTIME`), thrown on first use (constructing a `Queue` or `Producer`) on a runtime it does not support; importing the package does not throw. Its default message is "SureQ requires Node.js; this runtime is not supported".
- New queue option `storeCallTimeout` (default `30s`): every store call has a deadline. A call that has not answered by then fails with a retryable `StoreUnavailableError` (`outcomeUnknown` for a write) and starts reconnecting, so a hung store call no longer stalls the sweeper, a worker or an admin call for good; its late answer is ignored.
- A versioning and deprecation policy in the `@sureq/core` README: semver applies to the public API; the store contract may change in a minor release until it is declared stable; a deprecated API stays for at least one minor release before removal and is listed here.
- `SECURITY.md` (how to report a vulnerability privately) and `CONTRIBUTING.md` (setup, commands and rules).
- User documentation in the `user-docs` folder: getting started, guides, the API reference, writing a store and operations notes. The package READMEs now link to it.

**Changed**
- Only a running worker's poll loop, an active job's lease and handler timeout, a running scheduler, and a call still waiting on SureQ (an add waiting for the store or its filter, `ready()`, `health()`, `close()`) keep the process alive; every other SureQ timer is unref'd. A running scheduler now keeps the process alive until it stops.
- The built packages use Node built-ins and globals (`node:` modules, `Buffer`, `process`, `setImmediate`) only in a separate `platform-node` chunk; lint and the dist tests fail the build if any appear elsewhere.
- The types that public signatures use are now exported, type-only, so they can be named: from `@sureq/core`, `JobDefaults`, `LeaseOptions`, `PollingOptions`, `ReconnectOptions`, `TimeoutOptions`, `SerializeOptions`, `StoreErrorOptions`, `StoredBackoff`, `Jitter`, `FormatReason`, `RecordKind`, `ProducerEvent`, `Listener`, `NameData`, `NameResult` and `QueueBase` (the shared base of `Queue` and `Producer`; it cannot be constructed or extended); `@sureq/core/producer` re-exports the ones its own types use, including `QueueOptions` and the store contract's request and result types. Internal types and test-only members are no longer in the published declarations: `queue.internals`, the worker constructors, the worker's internal members, `MemoryStore`'s `faults` option, `dump()` and `unsafeMutate()`, and the `random` test seam on queue, worker and producer options. Runtime behaviour is unchanged.
- `new Queue` and `new Producer` check the store's `capabilities` as `defineCapabilities` builds them: a missing or mistyped flag or limit, or an object that is not deeply frozen, throws `InvalidOptionError` with paths under `store.capabilities`. Before, an incomplete object failed with a plain `TypeError` at the first call that read it.
- `health()` on a queue or producer whose store is not open yet opens it first, within the same `timeoutMs`, so the first readiness probe reports the real state. Before, a fresh queue reported `ready: false`, `status: 'degraded'` and `STORE_RECONNECTING` until its first store call.
- A job whose stored data, result or error is not valid JSON now raises `DeserializationError` (`DESERIALIZATION_FAILED`), which was declared but never thrown. A worker fails such a job for good without running the handler, and runs the other jobs it claimed with it; a batch worker leaves it out of the batch. Before, the worker reported `InternalError` "worker claim failed" and every job of that claim stayed active until its lease ran out, again on each retry. Reads throw it instead of a `SyntaxError` that could quote the stored text.
- The default `shutdownTimeout` is 25 s (was 30 s), so a default `close()` (about 28 s with `shutdownAbortGrace` and the releases) fits Kubernetes' default 30 s grace period. Set `shutdownTimeout: '30s'` to keep the old wait.
- **Breaking:** `Worker.running` is renamed `inFlight`. It counts concurrency slots in use (a batch takes one), not jobs, and the old name was easy to confuse with `isRunning()`. Replace `worker.running` with `worker.inFlight`.
- **Breaking (store contract):** `STORE_CONTRACT_VERSION` is 1 (was 2) and `SUPPORTED_CONTRACT_VERSIONS` is `[1, 1]` (was `[2, 2]`). No earlier version was published, so the first public contract is numbered 1. The contract itself did not change. A store that declares 2 is refused with `StoreContractVersionError`; set its `contractVersion` to `STORE_CONTRACT_VERSION`.
- `queue.formatVersion` and `producer.formatVersion` are typed `number` (were the literal `1`), `STORE_CONTRACT_VERSION` is typed `number` (was the literal `2`), `SUPPORTED_CONTRACT_VERSIONS` is typed `readonly [number, number]` (was `readonly [2, 2]`), and `@sureq/store-test`'s `SUITE_VERSION` is typed `string` (was `'1'`). A later version no longer changes these types.
- `runStoreConformance` throws `InvalidOptionError` for a `groups` entry that is not a group, with the closest group name as the suggestion. Before, a misspelt name such as `'stres'` quietly ran nothing extra.
- **Store contract:** a repeated `complete`, `fail` or `release` answers from the earlier job's tombstone even after a new job took its id (removed and added again, or superseded by a new add); before, it answered `not-active`, and a worker whose first answer was lost reported an unconfirmed outcome. A finished job superseded by a new add now leaves a tombstone. A new conformance test checks it; the store template does it.
- `reconnect.maxDelay` above 2^31 - 1 ms (about 24.8 days) throws `InvalidOptionError`, and the probe wait is capped there. Before, such a delay made Node fire the probe after 1 ms, so probes ran without pause and never reconnected.

**Removed**
- The `@sureq/memory` package. It only re-exported `MemoryStore`, which `@sureq/core` exports and uses by default; import `MemoryStore` from `@sureq/core` instead. Its conformance run, stress group included, now runs in `@sureq/store-test`.
- The queue and producer option `logPayloads`. No log line SureQ writes carries job data, so it did nothing but log a warning; passing it now throws `InvalidOptionError` (`unknown option`). To log job data, log it from the job events.

**Fixed**
- A batch worker holding a job whose stored data is not valid JSON no longer crashes the process when that job's lease is lost: the `leaseLost` event's job is built without its unreadable data.
- A claimed job whose stored error is not valid JSON is failed for good with `DeserializationError`, like one with unreadable data. Before, it stayed `active` with a renewed lease and the jobs claimed with it never started (a batch worker also lost a slot).
- A job with unreadable data deleted as it fails (no dead letter, `retention.failed: 0`) still emits `failed`, with no internal errors.
- `close()` while buffered adds are being sent after an outage lets the add already sent settle from the store; only the adds not yet sent are refused with `QueueClosedError`. Before, a stored add could be reported as not sent.
- `pause()` and `resume()` called together on one queue or producer are sent one at a time, so this pod's pause flag ends up agreeing with the store.
- `serializeError` keeps the result within `maxErrorBytes` when `name` or `code` hold many multi-byte characters, and shortens a non-ASCII message to fit instead of emptying it.
- `addBulk` with something that is not an array throws `InvalidOptionError` instead of a `TypeError`.
- The `retrying` event's job shows `waiting`, not `delayed`, for a retry with no delay, on stores that keep a due job `delayed` until it is claimed.
- `SerializationError.cause` for a value that cannot be serialized (a circular reference or a `bigint`) is a `TypeError` with a fixed message; it no longer carries the native message, which could name the value's properties, and an error thrown by a user's `toJSON` is no longer kept as the cause either.

**Tooling**
- Every public declaration and member of `@sureq/core`, `@sureq/core/producer` and `@sureq/store-test` has a doc comment, so editors show it on hover; a hygiene test fails when the API reports list one as undocumented.
- The public API of each package entry point (`@sureq/core`, `@sureq/core/producer`, `@sureq/store-test`) is recorded in an API Extractor report under `etc/`; `npm run api:check` (run in CI) fails when the built types differ from the committed report or a report uses `any`, and `npm run api:update` rewrites the reports.
- `npm run check:licenses` (run in CI and before publishing) fails when a published package has a licence outside MIT, ISC, Apache-2.0, BSD-2-Clause and BSD-3-Clause, a runtime dependency, or a peer dependency outside `@sureq`.
- A publish workflow, run by hand only, builds and checks the packages and publishes them to the public npm registry with provenance; a prerelease version is published under the `next` dist-tag, never `latest`.

## 0.3.0 - unreleased

Production basics: history, dead letters, retention, batches, progress, schedules, metrics and alerts, producer-only processes and rolling deploys across adjacent releases.

**Breaking changes**
- `STORE_CONTRACT_VERSION` is 2 and core accepts only stores that declare 2, so a store written for 0.2 must add the new methods (listed under Store contract) and set `contractVersion: 2`.
- a queue now checks the namespace's stored format before its first store call: a store written by a release it cannot read is refused with `StoreFormatError` from `ready()`, `add()` and the worker; `MemoryStore` no longer writes its namespace record on first use (`dump().meta` holds only the records `ensureNamespaceMeta` wrote).
- finished jobs are now deleted by default (queue option `retention`). The newest 1000 `completed` jobs are kept, and `failed` and `cancelled` jobs are kept for 14 days; a job kept for none stays readable for `resultGrace` (30 s) first. Dead letters are kept until they are redriven or removed. For 0.2 behaviour, set `retention: { completed: true, failed: true, cancelled: true }`.
- a job that fails for good is now a dead letter by default (queue option `deadLetter`, default on): it is kept until it is redriven or removed, and `retention.failed` does not apply to it. Set `deadLetter: false` to keep failed jobs under `retention.failed` only.
- ids of jobs added with `uniqueWhile: 'retained'` are no longer held forever: such a finished job is deleted after `retainedAge` (default 7 d) unless a rule gives it an age, so a later add with the same id is accepted as a new job. For 0.2 behaviour, set `retention: { completed: true, failed: true, cancelled: true }`.
- an `id` function now runs when `add` or `addBulk` is called, before the add waits for an unreachable store, instead of when the job is sent.
- `cancel` (queue, producer and `job.cancel()`) now reads the job first, since its retention policy depends on the job's name and `keep`: one more store `get` per call, plus a store `now` when the policy deletes the job at once. A job removed between that read and the cancel throws `JobNotFoundError`.

**Store contract**
- New store methods: `stats`, `getAttempts`, `clean`, `obliterate`, `redrive`, `setProgress`, `registerWorker`, `heartbeatWorker`, `unregisterWorker`, `listWorkers`, `purgeWorkers`, `ensureNamespaceMeta`, `getNamespaceMeta`, `putSchedule`, `getSchedule`, `listSchedules`, `deleteSchedule`, `listDueSchedules` and `fireSchedule`. New request fields: `hold`, `history` and `maxFormat` on `claim`; `started` and `batchId` on `renew`; `history` on `complete`, `fail`, `release`, `sweep` and `cancel`; `retention` on `complete`, `fail`, `sweep` and `cancel`; `deadLetter` on `fail` and `sweep`; `maxFormat` on `sweep`; `keepLast`, `retainExpired`, `name` and `excludeNames` on `clean`; and the `list` filters `deadLetter` and `name` with `orderBy: 'deadLetterAt'`. `NewJob` gains `keep`.
- `claim({ hold: true })` marks each lease `held`; the first `renew({ started: true })` (with the batch's `batchId`) clears it; `sweep` treats an expired held lease as a refunded release (`attempt` back, `crashCount` unchanged, always requeued) and closes its attempt record `released` by the sweeper. A non-boolean `hold` or `started`, or a `batchId` without `started: true`, is a `StoreRequestError`. Conformance group `batch`.
- `setProgress({ id, token, progress, field? })` is fenced like `renew`: it stores `{ value, updatedAt }` (store time) in the record's `progress` or `batchProgress` field and does not touch the lease; a stale token is refused and changes nothing. Every claim resets both fields to `null`; finishing keeps them. Conformance group `progress`.
- New job record fields: `deadLetter`, `retainUntil`, `keep`, `progress`, `batchProgress`, `redriveCount`, `lastError`, `attemptsTruncated`, `scheduleKey`, `scheduledFor` and `cancelReason` (set to `'user'` by `cancel`, otherwise `null`), and `lease.held`.
- `stats(scope, {})` returns `{ counts, oldestWaitingRunAt, deadLetters, now }` from one atomic read. The oldest waiting job ignores blocked (paused) and not-yet-due jobs, and `deadLetters` counts failed jobs with a dead-letter marker.
- `ensureNamespaceMeta` and `getNamespaceMeta` keep one format record per namespace (created at the caller's `current`, raised but never lowered, untouched by a caller that cannot read it), and `maxFormat` on `claim` and `sweep` skips records written in a newer format. Store reads reject only a record whose `formatVersion` stamp is broken; which versions a pod reads is decided by core.
- `redrive` moves failed jobs back to waiting (or delayed by `delayMs`), by `ids` or by a dead-letter `filter` (oldest first, up to `limit`), one conditional write per job: it keeps `seq`, `token` and attempt records, bumps `redriveCount` (and so the next attempts' `cycle`), copies `error` to `lastError`, and clears `deadLetter`, `retainUntil`, `finishedAt`, `progress` and `batchProgress`; outcomes carry `viaDeadLetter`, and a superseded id answers `duplicate-id`. The `deadLetter` field of `fail` (`{ reason?, keepMs? }` or `false`) and `sweep` (`{ keepMs? }` or `false`; the store derives `crashLimit` or `exhausted`) marks a final failure in the same write; a final `fail` or failing `sweep` without the field is stamped `legacy`. `list` takes `deadLetter: { reason?, olderThanMs? }` (with `state: 'failed'`), `name`, and `orderBy: 'deadLetterAt'` (needs the `deadLetter` filter; `seq` breaks ties).
- `getAttempts` pages a job's attempt records by token; `claim`, `complete`, `fail`, `release`, `sweep` and `cancel` open or close the record in the same atomic step as the job change, as their `history` request field says (`false` writes none, `{ max }` caps the records per job, default 50; `host` on `claim`). A closer that finds no open record inserts a closed one; a `cancel` without `history` (a producer's) only closes an open record, with no cap and no insert. A `renew` with `started: true` and `batchId` records the batch and `heldMs` on the open record. `MemoryStore.dump()` lists the attempt records.
- `registerWorker`, `heartbeatWorker`, `unregisterWorker`, `listWorkers` and `purgeWorkers` keep one worker record per namespace and worker id, all times in store time: register is an upsert starting `activeJobs: 0` and `status: 'running'`; heartbeat answers `ok: false` when the record is gone; `listWorkers` returns the records (those serving `queue` when given) with store `now`; `purgeWorkers({ staleIntervals, limit })` deletes at most `limit` records whose last heartbeat is older than `now - staleIntervals × heartbeatIntervalMs`, each record by its own interval, so a worker that beats slowly is never purged at a faster pod's pace. `MemoryStore` and the store template implement them; conformance group `workers`.
- `clean({ state, olderThanMs?, limit })` deletes up to `limit` (1 to 5000) jobs of one state at least `olderThanMs` old on store time, oldest `seq` first, each with its attempt records and its tombstone rule, and answers `{ removed, remaining }`; `state: 'active'` is a `StoreRequestError`. `obliterate({ force?, limit })` deletes a queue in pages and answers `{ removed, done }`: the first call counts active jobs and, unless `force` or none run, throws `QueueNotIdleError` and writes nothing; otherwise it sets the queue's obliterating marker, which makes `add`, `claim`, `sweep`, `redrive`, `setProgress`, `putSchedule`, `fireSchedule` and a `renew` with `started: true` throw `QueueObliteratingError`. The call that deletes the last job also deletes the history records, schedules and pause flag and clears the marker; the seq and token counters are kept. Conformance group `admin`.
- Retention: the `retention` field (`{ discard: true }` or `{ retainMs }`) of `complete`, a final `fail`, a failing `sweep` and `cancel` deletes the job with its attempt records in the same write (a repeat still answers from the tombstone) or sets `retainUntil` to store now plus `retainMs`; without it `retainUntil` is null, and a dead letter marked in the same write keeps its own. `clean` with `retainExpired` deletes jobs whose `retainUntil` passed, whatever their name, oldest first (with `olderThanMs`, also jobs a previous-release pod finished, by `finishedAt`, and only those `name` / `excludeNames` let through); with `keepLast: n` it keeps the newest `n` by `finishedAt` then `seq` and deletes older ones (only those at least `olderThanMs` old), never a dead letter or a `retained` job; in the age and `keepLast` modes `name` or `excludeNames` narrows what `clean` deletes. A job `clean` deletes takes the superseded records of its id (`id#seq`) along, and `retainExpired` also expires superseded records by their own `retainUntil`; neither ever deletes a superseded dead letter. `NewJob.keep` is stored as given and set by a replace. Conformance group `retention`.
- Store methods `listDueSchedules` (store-time due list plus `nextDueAt`) and `fireSchedule` (one atomic step: rev check, pause, early, overlap, job insert and schedule advance) are required of every store; `MemoryStore` and the store template implement them, and the conformance part `schedule-fire` of the group `schedule` checks them.
- Store methods `putSchedule` (with `expectedRev` compare-and-set; `null` means "must not exist"), `getSchedule`, `listSchedules` and `deleteSchedule` are required of every store; `MemoryStore` and the store template implement them, and the conformance group `schedule` checks them (`schedule-store:` tests).
- A superseded dead letter (a failed record with a dead-letter marker whose id a newer job took) is a dead letter still: `stats.deadLetters` counts it, `list` with the `deadLetter` filter returns it under its `id#seq` key, `redrive` by that key answers `duplicate-id`, and the filter form of `redrive` passes it by, so it never fills a page. Deleting the live job, `keepLast` and `retainExpired` never delete it; only `obliterate`, `remove({ id: 'id#seq' })` and an age-mode `clean` of `failed` do. Conformance test `dlq: a superseded dead letter stays a dead letter until it is removed`.
- Stores refuse a new job id ending in `#` and digits (core refused it already; `id#<seq>` is where a superseded record goes) and a `fireSchedule` job with a `singletonKey`, treat a request field set to `undefined` as absent, and write no tombstone for a job deleted longer than the tombstone lifetime after it finished. A paused `MemoryStore` claim reports `blocked` only for jobs within its `maxFormat`.
- New record fields and methods are required of every store; `examples/store-template` implements them all. Its `stats` scans every job, so its cost grows with the job count: a real adapter keeps the per-state and dead-letter counts in the writes that change them.

**Reliability**
- attempt history: one record per attempt (`AttemptRecord`: worker, host, start and end in store time, `waitMs`, `durationMs`, outcome `running | completed | failed | crashed | cancelled | released`, error, `endedBy`), written atomically with the job change; a crashed attempt's error is `LeaseExpired` with the last renew time and worker id. Read them with `job.getAttempts()` (every record, oldest first) and `queue.getAttempts(id, { limit, cursor })` (`{ attempts, truncated, nextCursor }`). Queue option `history` (default on, `maxRecordsPerJob` 50; `false` writes none); `truncated` counts the old records the cap dropped.
- dead letters: a job that fails for good is kept as a dead letter with `job.deadLetter: { at, reason }` (`exhausted`, `unrecoverable`, `retryRejected`, `crashLimit`, or `legacy` for a job a previous-release pod failed), written in the same store step that fails it. Read them with `queue.getDeadLetters({ reason, olderThan, limit, cursor })` and `queue.countDeadLetters({ reason })`; move failed jobs back with `queue.redrive(id | ids, { delay, priority, resetAttempts })`, `queue.redriveAll(filter, { limit, pageSize })` (paged, safe to re-run, not atomic) and `job.retry()`. A redriven job keeps its FIFO position and history; `job.redriveCount` and `job.lastError` are new. Events `deadLettered` (`{ job, reason }`) and `redriven` (`{ id, state, viaDeadLetter }`). Queue option `deadLetter` (default on, `false` disables; `warnAbove` default 10 000). `DuplicateJobError` gains `reason: 'superseded'`. A dead letter whose id a newer job took stays one under `id#seq`: listed, counted and kept until `queue.remove('id#seq')`, `clean('failed', ...)` or `obliterate`; redriving it throws `DuplicateJobError` (`skipped / duplicate-id` in a list); `redriveAll` passes it by. A redrive drops this pod's cached dead-letter count and wakes its workers. The types `RedriveOptions` and `RedriveSummary` are exported.
- adjacent minor releases share one store during a rolling deploy; a running pod whose store moves past the format it reads stops claiming, sweeping and firing schedules, finishes its active jobs, emits `degraded` and reports `ready: false` (warning `STORE_FORMAT_AHEAD`); `health()` gains `format` (`storeFormat`, `supported`, `degraded`). `StoreFormatError` gains `storeFormat`, `minReadable`, `maxReadable` and `sureqVersion` for a refused namespace. A failed format re-check is reported once per outage, and none runs while the store is reconnecting. A refused pod reports the refusal once, also when its only worker is paused.
- The `versionSkew` event (`{ workers }`) is emitted, checked every 60 s by a queue with a running worker, when live workers of a non-adjacent release share the queue, once per distinct set; it never blocks anything.

**Flow**
- Queue options `filter` and `filterTimeoutMs` (default 5000): a filter judges every add before it is stored and accepts it or rejects it with a reason. A rejection throws `JobRejectedError` (in `addBulk`, fills that input's slot; an atomic `addBulk` rejects with `BulkAddError`) and emits the new queue event `rejected` (`{ id, reason, reasonCode?, operation }`, `operation` typed as `FilterContext['operation']`); a filter that throws, times out or returns no verdict fails the add with `FilterError`. A rejected add makes no store call. `onDuplicate: 'replace'` filters the incoming data and a merge function's result is filtered before it is written. The types `FilterFn`, `FilterVerdict` and `FilterContext` are exported.
- `queue.processBatch(handler, { batchSize, batchDelay, batchMaxWait, onShutdown })` runs batches of unnamed jobs (`batchDelay` default 0; `batchMaxWait` default 20 x `batchDelay`, at least `batchDelay`) and returns a `BatchWorker` with `batch.flush()` and `batch.held`. Each job keeps its own lease, token, retries and write: the handler returns one result or `TaskFailure` per job, settles jobs early with `ctx.complete`/`ctx.fail` (a second call rejects with `AlreadySettledError`), or returns nothing to complete them all; a wrong-length result is a `BatchResultMismatchError`. Each `BatchJob` has its own `signal` and `cancelled`; a lost or cancelled job is dropped alone. `concurrency` counts batches; jobs held for a batch are never charged an attempt, also after a crash. `queue.process` with `batchSize` throws `InvalidOptionError`. The types `Batch`, `BatchJob`, `BatchContext`, `BatchHandler`, `BatchResults`, `BatchWorker` and `BatchWorkerOptions` and the class `TaskFailure` are exported.
- `ctx.progress(n, total?, message?)` and `ctx.progress(object)` report a job's progress, stored by a fenced write and read as `job.progress` (also from `getJob` on any pod) with `percent`, `etaMs` and `etaAt` derived from store times. Calls within the new worker option `progressInterval` (default 250 ms) are merged, the latest wins; the last value is written before the job completes or fails; a failed progress write is reported on `error` (once per outage of a worker's progress writes) and never fails the job. The object form is limited by the new worker option `maxProgressBytes` (default 4096). The new event `progress` fires once per stored value. Batch handlers get `ctx.progress(job, ...)` and `ctx.batchProgress(...)`, read as `job.progress` and `job.batchProgress`. The types `JobProgress` and `ProgressObject` are exported. `PayloadTooLargeError` gains `field` (`'data'` or `'progress'`).
- Queue option `retention` (`completed`, `failed`, `cancelled`, `byName`, `interval` 60 s, `pageSize` 500, `resultGrace` 30 s, `retainedAge` 7 d) and per-add `keep`. A `Keep` is `true` (forever), `false` or `0` (none), a count of the newest jobs, or `{ count, age }` (whichever is hit first); a job's own `keep` is `true`, `false`, `0`, a duration or `{ age }`. The policy is resolved when the job finishes: its own `keep`, then `byName`, then the queue's, then the default; `cancelled` follows `failed` unless set. `keep: 0` keeps the finished record (with its closed attempt) for `resultGrace`; with `resultGrace: 0` it deletes at finish and the `completed` or `failed` event carries `removed: true`. A job with its own `keep.failed` is never dead-lettered; `deadLetter: { keep: { age } }` bounds how long dead letters are kept. Jobs added with `uniqueWhile: 'retained'` are kept by age only (`retainedAge` unless a rule gives one), and a keep none on such a job is an `InvalidOptionError`. A cleanup pass runs on pods that run workers, at most 10 store calls per state per pass (a backlog goes on at the next sweeper tick); a producer-only fleet enforces no limits. `job.retainUntil` shows when a finished job may be deleted. Setting a bounded `retention.failed` while dead letters are on logs one warning (`failed: true` logs none). The types `Keep`, `JobKeep`, `RetentionOptions` and `RetentionPolicies` are exported (`Keep` and `JobKeep` also from `@sureq/core/producer`).
- `queue.clean(state, olderThan, { limit, pageSize })` removes the jobs of one state (`completed`, `failed`, `cancelled`, `waiting` or `delayed`) older than a store-time age (finished jobs by when they finished, waiting and delayed ones by when they were added), in pages of 500 by default (1 to 5000). It returns `{ removed, done }` and emits `cleaned` (`{ state, removed }`) once per call that removed any. `clean('failed', ...)` also empties the dead-letter queue.
- `queue.drain({ delayed, pageSize })` removes the waiting (and, optionally, delayed) jobs and returns `{ removed }`. Running jobs are not touched.
- `queue.obliterate({ force, pageSize })` deletes the whole queue: jobs, attempt history, dead letters, progress, settings and schedules, and emits `obliterated` (`{ removed }`) once, when done. It refuses with `QueueNotIdleError` while jobs run, unless `force` is set (their workers' later writes are refused). While it runs, `add`, `claim`, `sweep`, `redrive`, progress writes, schedule writes and schedule fires on that queue throw `QueueObliteratingError` (workers idle and the sweeper and scheduler skip quietly), and a call that died part-way is resumed by calling it again. It is refused (`InvalidOptionError`, `mixed-versions`) while a registered pod runs an older version or the namespace was last raised by one. Finish a rolling upgrade from 0.2 before using it, because 0.2 pods cannot be detected and ignore the marker. The calls are destructive and cannot be undone.

**Schedules**
- Schedule timing: 5-field `cron` expressions with month and weekday names and the aliases `@yearly`, `@monthly`, `@weekly`, `@daily` and `@hourly`, in an IANA `tz` (default `'UTC'`) with documented daylight-saving behaviour; and `every` intervals (`ms`, `s`, `m`, `h`, `d`; 1 s to 100 years) on a drift-free grid. The type `ScheduleTiming` is exported.
- `InvalidOptionError` issues carry a `reason` for a bad timing: `bad-cron`, `bad-timezone`, `no-occurrence` or `bad-interval`, and `bad-overlap` for a bad schedule `overlap`.
- `queue.previewSchedule(timing, n)`: the next `n` fire times (epoch ms) of a schedule timing, without storing anything.
- Schedules: `queue.upsertSchedule(key, def)` creates a durable schedule (a cron or `every` timing plus a job template) or brings it to `def`, safe to call from every pod on start-up. It resolves `{ schedule, action }` with `action` `created`, `updated`, `unchanged` or `stale`. The template's data is serialized at upsert; queue defaults apply when a job is made. An optional `version` is never downgraded: a lower one is `stale`, nothing is written, and a `scheduleStale` warning is logged once per key. A changed timing recomputes `nextRunAt` from store time; `runCount`, `paused` and the last fire are kept. Writes are compare-and-set on the record's `rev`; `ScheduleConflictError` after 10 tries. Keys are 1 to 200 UTF-8 bytes; the template options `id`, `delay`, `runAt`, `onDuplicate`, `uniqueWhile`, `singletonKey` and `idempotencyKey` are refused.
- Schedule management: `getSchedule(key)` (null when unknown), `listSchedules({ cursor, limit, state })` (key order, paged, `limit` 1 to 1000, default 100, `state` `'active'` or `'paused'`), `pauseSchedule(key)` and `resumeSchedule(key)` (idempotent; resume continues from the first tick after store now, with no catch-up), `deleteSchedule(key)` (false when there was none) and `nextRuns(key, n)` (the next `n`, 1 to 100, fire times in epoch ms; writes nothing). `ScheduleNotFoundError` for an unknown key on pause, resume and `nextRuns`. The queue events `schedulePaused`, `scheduleResumed` and `scheduleDeleted` (`{ key }`) are emitted after the store confirms a change.
- The scheduler: every pod with a worker on a queue runs that queue's schedule loop (`scheduler: { enabled, tickMs, batchSize }`, defaults `true`, 1000 ms, 50; `queue.startScheduler()` runs it without a worker, `queue.stopScheduler()` stops it). Each tick becomes exactly one job across all pods, judged by store time; missed ticks collapse into one catch-up job. A fired job has the id `sched:<key>:<scheduledFor>`, `runAt` at the tick and `job.schedule = { key, scheduledFor }` (`null` for other jobs); queue defaults apply at fire time.
- Schedule overlap: `'skip'` (default), `'queue'` (a backlog of up to `maxQueued`, default 10, run one at a time in tick order) or `'allow'`; a previous run is unfinished while waiting, delayed or active. Queue events `scheduleFired` (`{ key, scheduledFor, jobId }`), `scheduleSkipped` (`{ key, scheduledFor, reason: 'overlap' | 'backlog-full' }`) and `scheduleQueued` (`{ key, scheduledFor }`), emitted on the pod that fired.
- The queue `filter` runs once on a schedule's template at `upsertSchedule` (operation `'schedule'`), never when a tick fires.
- Health warning `SCHEDULER_STALE` when a running scheduler has not finished a loop turn in 5 x `tickMs`. The type `SchedulerOptions` is exported.
- Health warning `NO_SCHEDULER_RUNNING` when the queue has unpaused schedules and no live worker runs a scheduler. A scheduler started with `startScheduler()` on a pod without a worker is not in the worker registry, so the warning can show while that pod fires the schedules.
- The types `Schedule`, `ScheduleDefinition`, `ScheduleTemplate` and `UpsertResult` are exported.

**Observability**
- Metrics: `describeMetrics()` lists the catalogue; `queue.metrics()` returns a `MetricsSnapshot` (`{ at, scope, samples }`) from one `stats` read: `sureq_jobs` per state and `sureq_oldest_waiting_age_seconds` from the store, and this pod's counters (`sureq_jobs_added_total`, `sureq_jobs_finished_total`, `sureq_jobs_crashed_total`, `sureq_attempts_retried_total`, `sureq_jobs_rejected_total`), histograms in store time (`sureq_job_wait_seconds`, `sureq_job_processing_seconds`, `sureq_batch_held_seconds`) and window gauges (`sureq_job_processing_peak_seconds`, `sureq_success_ratio`, `sureq_throughput_per_second`); the window is kept in 1-minute buckets, and throughput divides by the time those buckets cover (at most the pod's uptime). Batch jobs are counted per job. Queue option `metrics: { window, buckets, maxNameLabels }` (defaults `'5m'`, `0.005` to `1800` s, 100). `queue.getOldestWaitingAge()` gives the oldest waiting job's age in ms (`null` when none; paused jobs are ignored). The types `MetricDescriptor`, `MetricSample`, `MetricType`, `MetricUnit`, `MetricsSnapshot` and `MetricsOptions` are exported.
- Alerts: queue option `alerts: { interval, depth, age, failureRate }` (interval default `'15s'`) evaluated per pod, also without workers (any `alerts` option, `{}` too, reads `stats` once per `interval`); edge-triggered with `resolveBelow` hysteresis. The queue event `alert` (`AlertEvent`), `queue.getAlerts()`, `HealthReport.alerts` and the `sureq_alert_firing` gauge. The types `AlertEvent`, `AlertRules` and `AlertType` are exported.
- `health()` reports `status: 'degraded'` while an alert fires; `live` is unaffected.
- Health warnings `DEAD_LETTERS_HIGH` (dead letters above `deadLetter.warnAbove`, from the count the last sweeper or alert tick read) and `SWEEP_STALLED` (this pod's sweeper has not finished a tick in 5 x `sweepInterval`). The sweeper's upkeep (the stats read, the registry purge and the retention pass) runs beside its sweeps, one at a time, so a slow step never delays a sweep. The count is cached per pod and refreshed only by that pod's ticks; `clean`, `drain`, `obliterate` and a redrive drop the calling pod's cache only.
- Live workers: `queue.getWorkers({ includeStale })` lists the workers of a queue from every pod as `WorkerInfo` (`workerId`, `host`, `pid`, `queues`, `concurrency`, `activeJobs`, `status`, `sureqVersion`, `formatVersion`, `scheduler`, `startedAt`, `lastHeartbeatAt`, `heartbeatAgeMs`, `stale`, `labels`), judged by store time: live within three heartbeat intervals, purged by the sweeper after ten. New worker options `host` (default `os.hostname()`), `labels` (at most 10, keys and values 1 to 64 characters) and `heartbeatInterval` (default 10 s, 1 s to 1 d). A worker shows `draining` and then removes its record on a graceful close. The type `WorkerInfo` is exported.
- Known limits: a held batch job whose pod died before its handler started counts in `sureq_jobs_crashed_total` while its attempt record says `released`; `metrics.maxNameLabels` slots are taken by the names of rejected adds too.

**Platform**
- `@sureq/core/producer`: a second entry point (ESM and CJS, with types) exporting `Producer`, the add side of a queue for processes that never run jobs. It adds, reads, cancels, removes, redrives, pauses, manages schedules and runs `clean`, `drain` and `obliterate`, with no worker, sweeper, scheduler, registry heartbeat, alerts or timer in its module graph; it never fires a schedule. Its options are the add-side queue options with `store` required; worker-side options throw `InvalidOptionError`. It emits `added`, `duplicate`, `rejected`, `error`, the admin events (`redriven`, `cleaned`, `obliterated`), `storeDisconnected`, `storeReconnected` and the schedule management events, and its event type lists exactly those. Its `cancel` sends no `history`, so it never caps or adds attempt records. It runs the start-up format check, and `close()` leaves the store open; until `close()` finishes, the admin calls (`remove`, `redrive`, `redriveAll`, `clean`, `drain`, `obliterate`) are still accepted, as on a queue. `Producer` is also exported from `@sureq/core`, and the `QueueClient` interface (`add`, `addBulk`, `ready`, `close`, `health`) is implemented by both `Queue` and `Producer`. The types `ProducerOptions` and `QueueClient` are exported.
- New error classes: `JobRejectedError` (`JOB_REJECTED`), `FilterError` (`FILTER_ERROR`), `AlreadySettledError` (`ALREADY_SETTLED`), `BatchResultMismatchError` (`BATCH_RESULT_MISMATCH`), `ScheduleNotFoundError` (`SCHEDULE_NOT_FOUND`), `ScheduleConflictError` (`SCHEDULE_CONFLICT`), `QueueObliteratingError` (`QUEUE_OBLITERATING`) and `QueueNotIdleError` (`QUEUE_NOT_IDLE`).
- `@sureq/core`, `@sureq/memory` and `@sureq/store-test` are 0.3.0; the peer range on `@sureq/core` is `^0.3.0`.

**Tooling**
- `@sureq/store-test` gains the conformance groups `history`, `retention`, `dlq`, `admin`, `progress`, `schedule`, `workers`, `meta`, `stats` and `batch`, and deliberately broken stores for the new methods (such as a non-atomic `fireSchedule` and a broken format record), each of which fails the suite.
- `npm run test:stress` also runs 100 000 schedule ticks (`SUREQ_STRESS_TICKS`); the stress and chaos runs cover batch workers, schedules and progress.
- Benchmarks: `bench:baseline` records throughput, claim and complete latency and idle polling load (`--compare` checks a run against `bench/baseline.json`), and `bench:batch`, `bench:progress` and `bench:observability` measure batching, progress writes and the cost of metrics and alerts.

## 0.2.0 - unreleased

Safe across pods: many pods share one store with no lost jobs and no double commits, and the store contract is public so you can bring your own store.

**Breaking changes**
- the worker option `pollIntervalMs` is removed; use `pollMin`/`pollMax` (defaults 100 ms / 5 s, adaptive with jitter). Passing it throws `InvalidOptionError` pointing at `pollMin`.
- For type users: `AddResult.added` is now `boolean` (`false` for a duplicate) and `AddResult` gained an optional `duplicate` field (`{ action, existingState, by }`).
- `MemoryStore` now implements the public store contract (`open`, `close`, `now`, `add`, `get`, `list`, `counts`, `update`, `remove`, `cancel`, `setPaused`, `isPaused`, `claim`, `renew`, `complete`, `fail`, `release`, `sweep`, `subscribe`). Call `open()` before using one directly; a `Queue` does it for you. The 0.1 method signatures and the `onCorrupt` claim callback are gone; `dump()` and `unsafeMutate()` remain test-only hooks.
- a finished job whose id is reused by a new add (under the default `uniqueWhile: 'pending'`) is no longer visible through `getJob`, `getJobs` or `getCounts`.
- a plain error thrown by a store (not a SureQ error) is now `StoreUnavailableError` (code `STORE_UNAVAILABLE`, still a `StoreError`) for every store operation, with `outcomeUnknown` true for writes; 0.1 gave `StoreError` (`STORE_ERROR`) unless the error carried a connection code.
- a `complete` or `fail` write that fails is repeated with the same token until the job's local lease deadline (after 50, 100, 200, 400 and 800 ms, then every second), and the worker's slot stays taken meanwhile; `completed`, `retrying` and `failed` are emitted only once the write landed. 0.1 parked the write and retried it in the background with no limit. An outcome that cannot be confirmed by the deadline is reported once on `error` (`StoreUnavailableError`, `outcomeUnknown: true`) and never counted as a failure; the sweeper recovers the job.
- `close({ timeoutMs })` (worker and queue) now overrides `shutdownTimeout`: handlers still running when it runs out are aborted with `ShutdownError` (`ctx.signal`), get `shutdownAbortGrace` more, and their jobs are released to `waiting` with the attempt refunded. A handler that settles after the abort is discarded, neither completed nor failed. 0.1 resolved at the timeout and left those jobs `active`, and without `timeoutMs` waited forever. `timeoutMs: 0` is accepted (abort at once). `close()` is bounded by the timeout plus the grace (plus up to one second for the last releases to answer), also when a claim, a sweep, a store write or the store's `subscribe`, unsubscribe or `close` hangs; concurrent calls return the same promise. `queue.close()` also waits for a worker already closing on its own, and a store `close` failure joins the `AggregateError` instead of replacing it.
- The repository is an npm-workspaces monorepo and the in-memory store and the conformance suite ship as their own packages (`@sureq/memory`, `@sureq/store-test`). `@sureq/core` keeps its name and entry points, and `getCounts()` keeps its shape.

**Store contract**
- The public store contract, experimental until it is frozen: the types `Store`, `Scope`, `StoreTime`, `Payload`, `JobRecord`, `NewJob`, `AddOutcome`, `ClaimRequest`, `ClaimResult`, `ClaimBlocked`, `FencedRejection`, `RenewRequest`, `RenewResult`, `CompleteResult`, `FailRequest`, `FailResult`, `ReleaseRequest`, `ReleaseResult`, `SweepRequest`, `SweptJob`, `SweepResult`, `CancelResult`, `RemoveResult`, `UpdateRequest`, `UpdateResult`, `ListRequest` and `JobCounts`, and the constants `STORE_CONTRACT_VERSION` and `SUPPORTED_CONTRACT_VERSIONS`.
- `StoreCapabilities` and `defineCapabilities()`: a store declares what it supports; missing flags are false, limits default to 255 id bytes and 1000 jobs per claim, and the result is frozen. A flag or limit given as `null` is refused, not defaulted.
- `Queue` accepts any `store` that implements the store contract; its `contractVersion` is checked when the queue first opens it.
- `queue.ready({ timeoutMs })` waits until the store is open and answers (rejecting with `StoreNotReadyError` after `timeoutMs`), and `queue.getStoreTime()` reads the store's clock.
- Lease, delay and retry instants come only from the store's clock; core sends durations, never pod time.
- `new MemoryStore({ finalsTtl })` accepts a duration such as `'10m'`.
- A paused `MemoryStore` queue reports `blocked: { reason: 'paused' }` (and `paused: true`) from `claim` only when it holds back a waiting job; an empty paused queue reports neither.
- `MemoryStore` enforces leases and fencing tokens: a stale or expired worker can no longer complete, fail or release a job; a repeated claim, complete, fail or release after a lost response returns the original outcome; expired leases are requeued by `sweep`, with a crash limit; `subscribe` wakes idle claimers.
- `getCounts().blocked` reports the waiting jobs a paused queue holds back (always 0 in 0.1).
- `MemoryStore` keeps a running count per state, so `counts` (and the `drained` check after every finished job) no longer scans every job.

**Reliability**
- `leaseDuration` (default 30 s, 1 s to 24 h) and `leaseDurationByName`, on the queue and per worker. Workers renew each running job's lease every third of its length.
- `ctx.token` and `job.token`, the attempt's fencing token; `job.lease` is now `{ owner, token, expiresAt }` while a job is active (it was always `null`).
- The `leaseLost` event (`{ job, token, reason }`): a lost lease aborts `ctx.signal` with `LeaseLostError` and discards the handler's outcome. A handler that ignores that abort frees its slot after `timeoutGrace` (default 5 s); its late result is ignored.
- Jobs whose lease expired (a crashed or stalled worker) are returned to `waiting` automatically by any pod running a worker for the queue, within `leaseDuration` plus up to 1.2 × `sweepInterval` (the interval is jittered by up to 20 %). Worker options `sweepInterval` (default 5 s ±20 % jitter, 500 ms to 1 d) and `sweepBatch` (default 100, 1 to 1000); one sweeper runs per queue object while any of its workers runs, set up by the first. Producer-only queues never sweep.
- Queue option `maxCrashes` (default 3): lease expiries after which a job is failed with `PoisonPillError` instead of being requeued. A job whose last attempt expires is failed with `StalledJobError`. The stored `PoisonPillError` does not hold the job's `jobId` and `crashCount`: they are filled in when the error is read.
- The `stalled` queue event (`{ job, previousWorkerId, crashCount, action: 'requeued' | 'failed' }`), once per swept job; a swept job that is failed also emits `failed`.
- A `sweepBatch` above the store's `maxClaimLimit` is capped to it, with one warning when the sweeper starts.
- `timeout` (default none) and `timeoutGrace` (default 5 s) on the queue, per worker and per `add` (the most specific wins, per field). At `timeout` after the handler starts, `ctx.signal` aborts with `JobTimeoutError`; the attempt then fails with that error through the normal retry path, as soon as the handler settles (its result is discarded) or after `timeoutGrace` at the latest (`abandoned: true`). An abandoned handler frees its slot and its late result is ignored. The per-add values are stored on the job record as the new `timeout` field; a stored value that is not a whole, non-negative number of ms is ignored. A `replace` duplicate changes only the one of the two it sets. `timeoutGrace: 0` abandons at once, so every timed-out attempt is recorded `abandoned: true` and warned about.
- Reconnect with backoff: one connection state per store object, `queue.connectionState` (`'connected' | 'reconnecting' | 'closed'`), and the queue events `storeDisconnected` (`{ error }`, once per outage) and `storeReconnected` (`{ downForMs, attempts }`), emitted on every queue sharing the store. While the store is unreachable it is probed with `now()` on the schedule of the queue option `reconnect` (`{ initialDelay: 100, maxDelay: 30_000, factor: 2, jitter: 0.2 }`, set by the first queue on the store).
- Queue options `onDisconnected` (`'reject'`, default, or `'wait'`), `maxWait` (default 10 s) and `maxBufferedAdds` (default 1000) decide what an `add` or `addBulk` does while the store is unreachable.
- An `add` or `addBulk` while the store is unreachable rejects at once with `StoreUnavailableError` (`outcomeUnknown: false`), or in `'wait'` mode waits until the store is back (at most `maxWait`, at most `maxBufferedAdds` waiting) and resolves only once the store acknowledged it. Closing the queue rejects waiting adds with `QueueClosedError`. An `add` whose response was lost is checked with `get` once the store is back and sent again only if it is not there. With a caller-chosen id (or id function) it is never sent again: it rejects with `StoreUnavailableError` (`outcomeUnknown: true`) carrying `jobIds`. An `addBulk` whose write outcome is unknown is not settled for you: it rejects with `BulkAddError` whose `jobIds` name every input sent. A held add keeps its first `maxWait` deadline when the store drops again while the held adds are sent.
- Claiming and sweeping pause while the store is unreachable; running handlers keep running, and an outage shorter than the lease loses nothing.
- `queue.ready()` retries on the `reconnect` schedule; a failure other than an unreachable store rejects it at once. Without `timeoutMs` it now gives up after 30 s.
- A finalising write the store refuses because the lease was lost is reported as `leaseLost`, not logged as a skipped write.
- Graceful shutdown: `worker.state` (`'created' | 'running' | 'stopping' | 'stopped'`, type `WorkerState`), and `closing`/`closed` events on the queue (`{ queue }`) and on each worker (`{ queue, workerId }`). Options `shutdownTimeout` (default 30 s) and `shutdownAbortGrace` (default 2 s) on the queue and per worker. A released job goes back to `waiting` at once with its attempt refunded and `crashCount` unchanged, so a deploy neither burns attempts nor counts as a crash.
- Queue option `signals` (default none, e.g. `['SIGTERM', 'SIGINT']`; `SIGKILL` and `SIGSTOP` cannot be listened for and are refused): the first signal calls `queue.close()`, a second exits the process with code 1 without releasing. Listeners are added at the first `process()` and removed when the queue closes.
- Once `queue.close()` has finished, `getJob`, `getJobs`, `getCounts`, `remove` and `getStoreTime` reject with `QueueClosedError`; they keep working while the queue is stopping. `add`, `addBulk`, `process` and `ready` reject from the moment `close()` is called; a `ready()` still waiting then rejects the same way.
- A claim in flight when `close()` starts has its jobs released without running them (`handlerStarted: false`).
- `close()` rejects with one `AggregateError` (`'shutdown: some leases could not be released'`), after finishing every step, when the store raised errors on release or a release could not be confirmed (by its lease deadline or close's) (also reported on `error`; the sweeper recovers that job, counting a crash).
- A queue closes the store it created when it is closed.

**Flow**
- Workers poll adaptively: `pollMin` (100 ms), `pollMax` (5 s), `pollFactor` (2) and `pollJitter` (0.2), settable on the queue or per worker. A local add, a freed slot or a store notification (`notify`, default true) wakes an idle worker at once.
- On a store whose capabilities say `skipLocked: false` (claimers block each other), each claim asks for at most 10 jobs and the poll wait jitters by ±50 %, within `pollMin`..`pollMax`. A paused queue's `pollMax` wait is jittered too, so pods do not poll in lockstep.
- A wake-up that arrives while a claim is out (a finished handler, an add) restarts the poll wait at `pollMin` instead of doubling it, so a job added after a busy burst is picked up within `pollMin` plus jitter.
- Caller-chosen job ids: `add(data, { id })` takes a string or a synchronous function of the data, and a queue-level `id` function applies to every add without its own. Ids are at most 255 UTF-8 bytes (or the store's smaller limit) and may not end in `#` and digits.
- Duplicate rules: `onDuplicate` (`'ignore'`, the default, `'replace'` or `'reject'`) per add or per queue, and `uniqueWhile` (`'pending'`, the default, or `'retained'`) for how long a job keeps its id. `'reject'` throws `DuplicateJobError`; `'replace'` overwrites the data and only the options this add set, on a waiting or delayed job.
- `onDuplicate` also takes a merge function `(existing, incoming) => data`: core reads the waiting or delayed job, merges and writes back guarded by its revision, retrying up to 10 times before `MergeConflictError`; a result that cannot be stored (`undefined`, a promise, not JSON) is `InvalidMergeResultError`. In a non-atomic `addBulk`, a merge function that throws fills only its input's slot, as an `InvalidMergeResultError` whose `cause` is the thrown value. A job that turned active is left alone and reported as `ignored`. The function must be pure: it may run more than once.
- `singletonKey` on `add`: at most one waiting or delayed job per key. Another add with a held key returns the holder (`by: 'singletonKey'`, or `DuplicateJobError` with `'reject'`) and never changes it; the key is free once its job starts or finishes. A job coming back for a retry while a newer job holds its key is still requeued, without the key.
- `job.idempotencyKey` on every job: the `idempotencyKey` add option when given (stored and returned unchanged), else `namespace:queue:id:seq`. It stays the same across retries, crash recovery and release, and differs for a later job that reuses the id. Pass it to payment and other external APIs; SureQ does not promise exactly-once effects.
- The `duplicate` event (`{ id, action, existingState, by }`), once per add that met an existing job, also for `'reject'`.
- Pause and resume: `worker.pause({ waitForActive })`, `worker.resume()` and `worker.isPaused(scope?)` stop one worker taking jobs, writing nothing to the store; `queue.pause()`, `queue.resume()` (both resolve `{ changed }`), `queue.pauseState()` and `queue.isPaused()` pause the queue for every pod through the store flag. Jobs a pausing worker already claimed go back to `waiting` unrun, attempt refunded. While the queue is known paused, a local add does not wake its workers; they check every `pollMax`. `queue.pauseState()` resolves the flag as this pod holds it after the read, so a newer change of its own wins over an older answer.
- `paused` and `resumed` events with the `PauseEvent` payload (`{ scope: 'local' | 'global', queue, workerId?, source: 'self' | 'observed', at }`) on the queue and on each worker; types `PauseEvent` and `PauseScope`.
- `queue.cancel(id)` and `job.cancel()`, resolving the exported type `JobCancelResult`: `{ cancelled: true, previousState, job }` or `{ cancelled: false, reason: 'already-terminal', state, job }`; an unknown id throws `JobNotFoundError`. A running job's `ctx.signal` aborts with `JobCancelledError` (at once in this queue's workers, at the next heartbeat or finalising write elsewhere) and its outcome is discarded; lease loss stays `LeaseLostError`. The `cancelled` queue event (`{ job, previousState }`), on the queue that called `cancel`.
- `drained` also fires after the last pending job is cancelled.

**Platform**
- The first `process()` on a store whose capabilities say `durable: false` (such as `MemoryStore`) logs one `warn` per store object: "store is not durable; jobs are lost on restart". Silence it with the worker option `acknowledgeVolatileStore: true`.
- `queue.health({ timeoutMs })` returns separate `live` and `ready` answers (liveness never depends on the store) plus per-worker loop and lease-renewal checks, store latency and warnings (`QUEUE_PAUSED`, `RENEWALS_LATE`, `STORE_RECONNECTING`); it never rejects at runtime and is bounded by `timeoutMs` (default 2 s). Types `HealthReport` and `HealthWarning`. `store.durable` reports the store's `durable` flag. `queue.ready()` waits for the store; `worker.isRunning()`.
- New error classes: `StoreRequestError` (`STORE_BAD_REQUEST`), `StoreContractVersionError` (`STORE_CONTRACT_VERSION`), `StoreNotReadyError` (`STORE_NOT_READY`), `CapabilityError` (`UNSUPPORTED_CAPABILITY`), `LeaseLostError` (`LEASE_LOST`), `JobTimeoutError` (`JOB_TIMEOUT`), `JobCancelledError` (`JOB_CANCELLED`), `ShutdownError` (`SHUTDOWN`), `StalledJobError` (`JOB_STALLED`), `PoisonPillError` (`POISON_PILL`, unrecoverable), `DuplicateJobError` (`DUPLICATE_JOB`), `MergeConflictError` (`MERGE_CONFLICT`), `InvalidMergeResultError` (`INVALID_MERGE_RESULT`) and `JobNotFoundError` (`JOB_NOT_FOUND`).

**Tooling**
- Added `@sureq/store-test`: `runStoreConformance` checks a store against the store contract (claims, leases, fencing, sweeping, release, cancel, pause, clock), with a JSON report, fake and real-time modes, and a `conformant` verdict. The `dedup`, `singleton`, `idem` and `merge` groups check the duplicate rules; pass `core(store, scope)` (a queue built in the given namespace and queue) to also run the concurrent merge test. The opt-in `stress` group (`groups: ['stress']`, size from `SUREQ_STRESS_JOBS`) races many claimers and adders on one queue.

- `@sureq/memory` passes the conformance suite in CI, and every deliberately broken store in the suite's own tests fails it.
- `examples/store-template`: a commented reference store adapter that passes the full conformance suite (not published).

- Job metadata: `attempt`, `createdAt`, `startedAt`, `finishedAt`, `workerId`, `failedReason` and more.
- Named job types: `process({ name: handler })`, typed per name with a name map.
- Payload and result size limits (`maxPayloadBytes`, `maxResultBytes`, default 1 MiB).
- `addBulk` atomicity is explicit (`{ atomic: true }`); otherwise each input gets its own outcome.
- `job.remove()` and `queue.remove(id)` for waiting, delayed and finished jobs.
- `defaultJobOptions` per queue.

**Flow**
- Per-worker concurrency.
- Priority, with `first: true` to go ahead of jobs of the same priority.
- FIFO or LIFO ordering per queue.
- Delayed jobs (`delay`, `runAt`), timed by the store clock.

**Reliability**
- `maxAttempts` (default 3), counted in the store so it survives a move to another process.
- Backoff: fixed, exponential with jitter and cap, and named custom strategies.
- Store errors surface as typed errors and `error` events; outcome writes are retried, then kept and retried in the background.
- `UnrecoverableError` and `ctx.fail(err, { retry })`; oversized or unserializable results are never retried.
- Error serialization: name, message, stack, cause chain and custom fields survive storage.
- `retryIf(err, job)` decides per error whether to retry.

**Platform**
- Local events: `added`, `active`, `completed`, `retrying`, `failed`, `drained`, `error`.
- Pluggable logger (`consoleLogger`, `pinoLogger`, or `false`).
- `MemoryStore`, exported from the main entry.
- Every stored record carries `formatVersion`.
- TypeScript-first, ESM + CJS, Node 22+, no runtime dependencies.
- Option validation at startup with closest-name suggestions, and a typed error catalogue.

**Breaking changes**
- None: first release. Breaking changes between 0.x releases will be listed here.

**Known limits**
- Memory store only: jobs are lost when the process exits.
- A process death leaves `active` jobs stranded; nothing reclaims them yet.
- Finished jobs are never removed automatically.
- `close()` has no deadline unless `timeoutMs` is given.
- `maxPayloadBytes` and `maxResultBytes` default to 1 MiB.
